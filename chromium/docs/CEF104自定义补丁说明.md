# CEF 104 自定义修改说明

以下仅说明本工作区为 macOS CEF 104 构建添加的修改。目标是生成 arm64 和 x86_64 双架构 Framework，并提供最低 macOS 11.0、12.0 两套配置。

## 1 支持指定 IPC 基础标识

**提交：** CEF `dea6f60`；Chromium `5c3ede40c4` 仅更新 CEF 子仓库引用。

**文件：** [cef/libcef/common/util_mac.mm](../src/cef/libcef/common/util_mac.mm)

- **原因：** App Sandbox 下，Chromium 的 Mach IPC 服务命名需要配合已授权的 App Group，原有应用 Bundle ID 不一定适用。
- **修改：** `GetMainBundleID()` 优先读取 `--base-bundle-id`；未指定时仍读取应用原来的 Bundle ID。
- **影响：** 改变进程内的 `base::mac::BaseBundleID()`，影响使用该值的 IPC 名称、沙盒参数和临时路径前缀等。不会修改 Info.plist、签名或自动授予 App Group 权限。主进程和相关子进程必须使用一致参数。
- **平台：** 仅 macOS，两个架构均适用；Windows/Linux 不变。

## 2 兼容旧 Clang 的 SDK 环境判断

**提交：** Chromium `6ed1e0cfed`

**文件：** [build/config/mac/BUILD.gn](../src/build/config/mac/BUILD.gn)

- **原因：** 较新 SDK 会检查 Clang 15 不认识的 target environment 名称，可能导致平台判断错误。
- **修改：** 新增默认关闭的 `cef_legacy_clang_modern_sdk` 开关。开启后将 `__is_target_environment(x)` 统一定义为 0，并关闭内建宏重定义警告。
- **影响：** 影响使用该 macOS 构建配置的所有目标及其头文件条件编译，不只影响 libcef。仅适用于原生 macOS，不能直接用于 Catalyst 或模拟器。
- **当前状态：** 最终使用 SDK 12.3，但两个架构仍开启此选项；尚未验证在 SDK 12.3 下关闭它是否可行。
- **平台：** Windows/Linux/Android 的常规构建配置不变。

## 3 补齐 SDK 部署版本宏

**提交：** Chromium `7b6dc45799`

**文件：** [build/config/mac/BUILD.gn](../src/build/config/mac/BUILD.gn)

- **原因：** 较新 SDK 使用通用部署版本宏，而 Clang 15 提供的是 macOS 专用宏。
- **修改：** 在上述兼容开关开启时，将 `__ENVIRONMENT_OS_VERSION_MIN_REQUIRED__` 定义为 `__ENVIRONMENT_MAC_OS_X_VERSION_MIN_REQUIRED__`。
- **影响：** 让头文件条件编译读取实际的最低系统版本。不会硬编码版本，也不会绕过 API 可用性限制；当前最低版本由所选配置设为 11.0 或 12.0。
- **平台：** 当前两个 macOS 架构均启用，其他平台常规配置不变。

## 4 明确系统库的链接搜索路径

**提交：** Chromium `60056c2cd6`

**文件：** [build/config/mac/BUILD.gn](../src/build/config/mac/BUILD.gn)

- **原因：** 旧版 LLD 搜索宿主默认路径时，会因 `/usr/local/lib` 等目录不存在而产生警告，影响构建。
- **修改：** 在兼容开关开启时，使用 `-Wl,-Z` 禁用默认标准搜索目录，再显式加入所选 SDK 的 `usr/lib` 和 `System/Library/Frameworks`。
- **影响：** 改变使用该配置的 macOS 目标的链接搜索规则。依赖宿主默认目录的第三方库需要显式配置路径。不会修改系统库实现、运行时 rpath 或动态库 install name。
- **平台：** 当前两个 macOS 架构均启用；其他平台链接配置不变。

## 5 修正 App Sandbox 下的进程角色断言

**提交：** Chromium `cf1271eb47`

**文件：** [content/common/pseudonymization_salt.cc](../src/content/common/pseudonymization_salt.cc)

- **原因：** 原代码用“未被沙盒隔离”判断 Browser 主进程，但开启 App Sandbox 后主进程本身也在沙盒内，可能误触发断言。
- **修改：** macOS 改为检查命令行没有 Chromium 子进程的 `--type` 参数，允许 Browser 进程按需初始化 salt。
- **影响：** 仅在 `DCHECK_IS_ON()` 时改变断言条件。salt 的生成、存储和返回逻辑不变，也没有关闭沙盒。子进程仍应从父进程获取 salt。
- **平台：** macOS 两个架构相同；其他平台保留原有检查。依赖宿主正确保留 `--type` 进程角色约定。

## 6 分离两个架构的 V8 snapshot

**提交：** Chromium `5efbe1e9ba`、CEF `ee94131`，两项需要配套。

**文件：** [gin/v8_initializer.cc](../src/gin/v8_initializer.cc)、[cef/BUILD.gn](../src/cef/BUILD.gn)

- **原因：** 两个架构的默认 snapshot 原来都叫 `snapshot_blob.bin`，合并 Framework 时会重名。snapshot 与架构相关，不能像 Mach-O 一样用 lipo 合并，也不能任意保留其中一份。
- **CEF 提交 `ee94131`：** 在 `cef/BUILD.gn` 新增 `cef_framework_v8_snapshot` 打包目标。当 `is_mac` 且 `v8_use_external_startup_data` 时，将构建输出 `snapshot_blob.bin` 复制为 Framework 内的 `snapshot_blob.$target_cpu.bin`，并让资源目标依赖它。这项提交改变的是打包规则，不是加载代码。
- **Chromium 提交 `5efbe1e9ba`：** 在 `gin/v8_initializer.cc` 按当前 CPU 架构选择对应文件；非 bundle 的 macOS 工具继续读取原名。同时将 CEF 子仓库引用更新到 `ee94131`。这项提交负责加载逻辑及配套版本引用。

| 资源 | arm64 | x86_64 |
| --- | --- | --- |
| 默认 snapshot，新增命名 | `snapshot_blob.arm64.bin` | `snapshot_blob.x64.bin` |
| Context snapshot，沿用原命名 | `v8_context_snapshot.arm64.bin` | `v8_context_snapshot.x86_64.bin` |

- **影响：** 改变 macOS bundle 的资源文件约定，单架构包也需要采用新命名。加载和打包规则不能只改一边；默认 snapshot 没有旧文件名回退。gin 属于 Chromium 公共代码，其他 macOS bundle 若走相同加载路径，也需检查其打包规则。
- **平台：** Windows/Linux/Android 保留原逻辑。本次支持的 macOS 架构为 arm64、x86_64。

## 7 提供可选 SDK 头文件映射

**提交：** Chromium `8a50883629`

**文件：** [build/config/mac/BUILD.gn](../src/build/config/mac/BUILD.gn)

- **原因：** 尝试较新 SDK 时，旧编译器无法处理部分头文件声明，需要一种不直接修改系统 SDK 的兼容方式。
- **修改：** 新增 `cef_legacy_sdk_overlay` 参数。兼容开关开启且参数非空时，传入 `-ivfsoverlay`，让编译器读取指定的头文件映射。
- **影响：** 启用后的具体影响取决于映射内容，可能改变声明和条件编译，需单独检查 ABI 兼容性。补丁本身不修改系统 SDK。
- **当前状态：** 最终使用 SDK 12.3，两个架构均未启用此映射，因此不影响本次产物。
- **平台：** 仅接入 macOS 构建配置。

## 8 修复 Intel 的 PAGE_SIZE 编译错误

**提交：** Chromium `8fbe6ed2ed`

**文件：** [base/process/process_metrics_mac.cc](../src/base/process/process_metrics_mac.cc)

- **原因：** 原代码在 Intel 上用 `static_assert` 检查页大小，但当前 SDK/部署目标组合下 `PAGE_SIZE` 可以是运行时变量，不能用于编译期断言。
- **修改：** Intel 改为与 ARM64 一样，使用 `DCHECK_EQ(PAGE_SIZE % 1024, 0u)` 在运行时检查。
- **影响：** 内存统计计算公式和页大小取值不变。Intel 的检查从编译期变为运行期；关闭 DCHECK 时不再执行这项检查。ARM64 保持原有行为。
- **平台：** 仅 macOS 内存统计实现，Windows/Linux 不变。

## 验证范围

macOS 11.0、12.0 两套配置均已完成 arm64、x86_64 增量构建和 Universal 合并。四个核心 Mach-O 的双架构、最低系统版本、SDK 12.3 和两套 V8 snapshot 均已验证。

Intel Mac 尚未完成完整构建，macOS 11/12 也尚未完成对应系统实机运行。文中的“其他平台不变”依据源码的平台条件和构建配置，不代表已经完成跨平台回归。当前结果见 [验证矩阵](../../docs/verification-matrix.md)。
